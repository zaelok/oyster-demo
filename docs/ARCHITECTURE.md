# OYSTER — Orchestration with Your Success metrics, Transparent Evaluation & Routing

*A user-cost-aware agent orchestration engine. Status: design locked 2026-07. This document specifies the demo slice — a deliberately static subset of a larger vision (see §5). The demo's claim is narrow and measurable.*

---

## 0. Problem & Position

**Problem.** Existing LLM orchestration — open-source frameworks and commercial auto-routing alike — optimizes with *someone else's* objective function. The routing policies, cost tradeoffs, and quality definitions are set by the vendor or the framework, tuned on aggregate benchmarks, opaque to you, and occasionally at odds with your interests: a token seller's ROI is not your ROI. Your context may be *in* the prompt; it is not in the *optimizer*.

**Landscape.** Cost-aware model routing is a hot lane in 2026 — RouteLLM routes single queries between strong and weak models using a classifier trained on Chatbot Arena preference data; LLMRouter aggregates 16+ academic routers of the same shape; LiteLLM does ops-level provider routing (fallback, cheapest-provider); hosted routers (Not Diamond, OpenRouter) optimize on their own aggregate data under their own incentives. All of these answer *"which model for this query"* — a single-step decision, with priors learned on **their** data and objectives set by **their** authors. None of them answer *"which multi-step path for this task, under my budget, by my definition of success"* — and none make the decision auditable.

**Position.** Turn it around and start from the user story: a system that optimizes for **your** context, **your** cost structure, **your** success metrics — with the objective function stated explicitly, the priors measured on your own corpus rather than learned on someone else's, and every decision traceable. On these principles: **OYSTER** — **O**rchestration with **Y**our **S**uccess metrics, **T**ransparent **E**valuation & **R**outing.

**Scope of this slice.** OYSTER aims to be scenario-generic — the graph model, the selection objective, and the measurement machinery (§1-§3) make no reference to code review. But a generic claim is only credible when demonstrated on a concrete task with an honest metric, so the MVP deliberately narrows to **one scenario: pull-request review**. It is chosen because quality has an objective ground truth here (seeded bugs with golden labels — no human-preference judging), because its cost structure is rich enough to make path selection non-trivial (variable diff sizes, cacheable context, cascade and iteration each with real cost deltas), and because it is a task every engineering team runs daily. The success metric for this scenario — **bugs caught per dollar** — is one instantiation of "your success metrics," not the definition of it; swapping the scenario means swapping the corpus and the metric, not the engine.

**Claim under test:** an orchestrator operating on a uniform graph representation can select, under an explicit cost budget, a review strategy whose measured bugs-caught-per-dollar beats any fixed single strategy — and can show its work.

**Deliverable:** `git clone` → `run` → a table: `path → cost($) → bugs caught → $/bug`, generated by the same code for every path, on a seeded-bug corpus with golden labels. Target: reproducible end-to-end in under 5 minutes with a reviewer's own API key.

## 1. Graph Model

### 1.1 Nodes are roles; models are attributes

A **node** is a role — a unit of review function: `cheap-scanner`, `deep-reviewer`, `critic`. A node carries:

- `role`: what it does (prompt template + output contract)
- `model`: which model executes it (e.g. haiku / sonnet) — **a configuration attribute, not node identity**. Swapping the deep-reviewer from sonnet to opus is a config change, not a graph change. This keeps the combinatorics contained and lets the selector optimize over model bindings later without a redesign.
- `cost prior`: see §1.3
- `quality prior`: see §1.4

### 1.2 Edges carry findings; the diff is ambient context

An **edge** is a handoff of *findings*: the downstream node receives the upstream node's structured output (flagged hunks, suspected issues), not a re-narration of the input. The **original diff is global cached context** — addressed, not copied, by every node. This mirrors how prompt caching actually works (the diff is the cache-hit prefix) and keeps edge payloads small and meaningful.

**Edges have cost**: `edge_cost = downstream input tokens attributable to upstream output`. A cascade is only worth its edge if the upstream findings shrink downstream work by more than the handoff adds.

Every result records its full path. **The audit trail is not a byproduct; it is the point** — each caught (or missed) bug is traceable to the sequence of nodes and handoffs that produced the verdict.

### 1.3 Cost is a vector

`cost = (dollars, latency)`.

- `dollars = input_tokens × rate_in × (1 − cache_hit_discount) + output_tokens × rate_out` — input and output priced separately because the cached diff prefix discounts input heavily on multi-node paths.
- `latency` = wall-clock per node, summed along the critical path of the subgraph.

### 1.4 Quality priors are measured, not assumed

The quality prior of a node config is its **empirically measured catch-rate on the seeded-bug corpus** (§3): run each node config over the corpus once (a calibration pass), record `P(catch | bug category)` per node. It is a table, not a model — reproducible from the repo, honest about its scope (these priors are valid for this corpus and these bug categories, nothing more).

*Deferred (Future Work): learning quality priors from public review data (e.g., merged-PR review outcomes). That is a research project with label-noise problems of its own; the slice measures instead of estimating.*

### 1.5 Why a graph and not hardcoded pipelines

Because **the selector operates on a uniform structure, not on named alternatives.** With hardcoded pipelines, "choose the best strategy" is an if/else over function names, and every new strategy is new selection code. With nodes and edges carrying cost and quality data, selection is **one algorithm over data**: enumerate valid subgraphs, score each on predicted quality and cost, take the argmax under budget. Adding a strategy is adding *data* — a node, an edge — with zero change to selection or measurement code. The proof is in the deliverable: the $/bug table is generated by the same code for every path, which is only possible because paths are data.

(Scale-out is the second-order benefit, not the argument: more roles, more model bindings, more paths — same selector. And the graph is what separates OYSTER from single-step routers: RouteLLM-style systems map one query to one model; a path through this graph is a *task-level strategy* — cascade, iterate, or single-pass — selected as a unit, priced as a unit, audited as a unit.)

## 2. Selection Objective

Over the enumerated candidate subgraphs `G_i` (the demo ships three — §2.2):

```
maximize   predicted_quality(G_i)          # Σ over nodes of calibrated catch-rate, category-weighted
subject to dollars(G_i) ≤ budget
```

with a **lexicographic pre-filter**: first drop any `G_i` whose predicted latency exceeds the caller's tolerance, then optimize cost/quality among the feasible set. If the feasible set is empty, **return early and say so** — report the cheapest infeasible option and its latency/cost so the caller can raise the budget or relax the tolerance. The engine never silently degrades.

### 2.1 Iteration is a path, not a belief

One refinement round — `review → critique → re-review` — is expressed as a **bounded unroll**: the reviewing role appears twice in the DAG (k=2), structurally acyclic, terminating by construction. It enters the candidate set as an ordinary path with its own measured cost and catch-rate. **Whether iterating is worth it is not a stance; it is a row in the table.** (In the corpus runs, the table reports what one refinement round buys and at what multiple of cost.)

### 2.2 The three shipped paths

- **Path A** — single cheap pass: `cheap-scanner(cheap-model)` over the diff.
- **Path B** — cascade: `cheap-scanner(cheap-model) → deep-reviewer(strong-model)`, where the deep reviewer receives only the scanner's flagged hunks (edge = findings; diff = cached context).
- **Path C** — bounded iteration: `deep-reviewer → critic → deep-reviewer` (k=2 unroll).

(`cheap-model` / `strong-model` are config bindings — the repo pins concrete model IDs in one place; the doc stays version-agnostic. Three paths is the smallest set on which "selection as one algorithm over data" is demonstrably true and the iteration question is measurable.)

## 3. Evaluation Method

- **Corpus**: N small diffs (target: 10-15), each seeded with known bugs across three categories — logic, security, style — with golden labels (I planted them; the labels are the ground truth by construction).
- **Calibration pass**: every node config runs the corpus once → per-node `P(catch | category)` table → these are the quality priors of §1.4.
- **Evaluation runs**: each shipped path runs the corpus end-to-end; the engine logs per-path: total dollars (from token counts × published API rates), wall latency, bugs caught vs golden labels.
- **The deliverable table** (auto-generated, committed as `results.md` with timestamp + model versions):

  | path | $ total | bugs caught / seeded | $/bug | p50 latency |
  |---|---|---|---|---|

- **Reproduction**: `make eval` with the reader's own API key regenerates the table. A mock-model CI job (fixed fake responses) proves clone-and-run without spending anyone's tokens.
- **What the numbers do and don't show**: catch-rates are corpus-specific; N is small; seeded bugs are cleaner than wild bugs. The table supports the *claim* (§0) — that selection over measured paths is possible and auditable — not a general benchmark of any model's review ability.

## 4. Non-Goals (this slice)

- **Unbounded runtime cycles** (convergence-criterion stopping). A cyclic graph requires a termination argument — cost budget as a **variant function**, monotonically decreasing per traversal. The DAG slice guarantees finite execution structurally; the variant-function treatment for true cycles is designed (vision doc) and is v2.
- **Runtime re-planning** (switching paths mid-run on intermediate results) and **dynamic node creation** — not on the MVP critical path; both need evaluation machinery of their own.
- **Learned quality priors** (§1.4 note) and **semantic result caching** — future work, one sentence each in the README.
- **Any hosted service.** The deliverable is a reproducible repo, not a deployment.

## 5. Relation to the Vision

The full thesis is a dynamic, cyclic, weighted directed graph with online subgraph selection under a cost budget and offline consolidation as the evolution mechanism. The slice ships the load-bearing subset — uniform graph representation, measured priors, budgeted selection, full auditability — and defers exactly the parts whose hard problems (termination, convergence, learned priors) are named in §4 rather than hand-waved. Restraint is the point: the slice proves the claim it makes, and only that claim.
